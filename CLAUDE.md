# monl — project memory for Claude Code

## What monl is

PIVOT (point 40 of docs/design_decisions.md): monl is now an
ORCHESTRATION platform. `./monl` (src/cli.py) runs an AI-free guided dialogue
(src/dialogue_engine.py) that produces the spec, compiles the backend,
and generates a frontend contract (src/frontend_contract.py:
frontend_contract.json + FRONTEND_PROMPT.md) intended for an external UI AI.
`monl run` checks consistency (fingerprints in monl.json) and mounts
frontend/ at /site through a serve.py wrapper — app.py remains sealed.
`monl update` recompiles and reports the contract delta. The dialogue
starts with a catalog of 10 application templates (src/app_templates.py,
point 45 — each template is tested as compilable with all-no/all-yes) and
uses strict input, entirely deterministic: no AI, no network calls. The
produced spec is revalidated by the real parser before being written.
`monl frontend` calls AI either through an API key — Anthropic, or any
provider using the OpenAI dialect via the `OPENAI_COMPATIBLE` table and the
`--provider openai-compatible` escape hatch (point 69) — or through a command
line agent (`--provider claude-code|codex|gemini`, or
`--agent-command` for any other, point 69; subscription authentication — point 43);
`monl import` handles copy/paste from claude.ai (point 42). In every case:
same safeguards, same re-check (consistency + smoke test). The protected
artifact fingerprint safeguard does NOT depend on which agent is used — never
bypass it by adding a path. ATTENTION: each compiled project gets its OWN
CLAUDE.md (generated by write_project_claude_md) — do not confuse it with this
file, which is the memory for the monl repository itself. The core
below is unchanged and remains the source of truth:

DSL compiler (`.ml` files — the old `.yaml` extension is still accepted) that generates complete applications
(FastAPI + SQLite + JWT) from declarative specs. Pipeline:
Lark grammar (`src/parser.py`) → validator + security audit
(`src/ast_validator.py`) → normalized AST → generator (package
`src/generator/`)
→ `app.py` / `schema.sql` / `sandbox_ai.py` + `frontend_contract.json` /
`FRONTEND_PROMPT.md` (orchestrator layer, see src/cli.py).

## Working method — non-negotiable

**Every change is proven by real execution, never by code review alone.** In practice:
- Actually compile (`python3 -m monl.main exemples/03_reseau_social.ml`,
  from the root with `src/` on PYTHONPATH — or `./monl compile`)
- Restart a real server (`python3 -m uvicorn app:app --host 127.0.0.1 --port PORT`)
- Make real calls (`curl`, or a Node+jsdom script for frontend JS —
  see `/tmp/jsdom_test/` in previous sessions, recreate if needed:
  `npm install jsdom` then load the generated HTML with `runScripts: "dangerously"`)
- Run the test suite: `python3 -m pytest tests/ -q` (1450 tests passing and
  16 declared skips — the only legitimate ones, integration PostgreSQL
  not requested, each named by `-rs`; `tests/test_demo.py` relies on the
  versioned `demo/` directory — do not delete it. The demo is **CodexShop**,
  a stationery shop exercising the entire commerce flow; only its INPUTS are
  tracked (`spec.ml`, `frontend/`, `assets/`), never its compiled output or
  its `.jwt_secret`. `test_design_contract.py` no longer uses it: it builds
  its own spec)

Several real bugs (the order of `FOREIGN KEY` constraints, a collision with a
reserved SQL keyword, missing `scrollIntoView` masking a real success,
over-escaping of backslashes across Python templating layers, a foreign key
mechanism that decremented the wrong record) would NEVER have been revealed
by simple code review — do not skip this step to go faster.

**Verification tools** (point 63) — three questions, three commands:
```bash
ruff check src tests                                  # zero expected: every
                                                      # report is a real one
python3 -m pytest tests/ -q --cov=src --cov-report=term-missing   # 89 %
python3 -m pytest tests/test_architecture.py -q       # this file's boundaries,
                                                      # verified
```
The `ruff` exceptions live in `pyproject.toml` and each has a reason — adding
one without a written reason reopens the door that point 63 closes. CI
(`.github/workflows/ci.yml`) reruns lint + suite.

**Always clean before/after compilation** (since point 64, the test suite no longer dirties the root: this cleanup concerns only YOUR
manual compilations):
```bash
rm -f app.py schema.sql sandbox_ai.py .jwt_secret *.db \
      frontend_contract.json FRONTEND_PROMPT.md FRONTEND_UPDATE_PROMPT.md monl.json serve.py
find . -name "__pycache__" -exec rm -rf {} +
```

**Recurring environment trap**: processes launched in the background
(`&`) in a tool call do NOT survive to the next call — starting a server AND
making test requests must happen in the SAME bash call.

## Product vision: capability ecosystem, built brick by brick

Explicit and settled decision: NO multi-DSL or multi-target IR for
now (a project of an entirely different scale, to reconsider only after
several real capabilities have been proven). Each brick is small,
tested before the next. Progression from simple to complex, with an
anonymous social network as the final test bench.

1. **`capability auth`** — the dormant brick WOKE UP at point 95.
   It constrains account identifier FORM:
   `capability auth` + `identifier: email, phone` (OPTIONAL indented block — a
   spec from before this point compiles identically, and `None` ≠ `[]`: guessing
   “email by default” would lock all existing projects).
   **The substance is not validation, it is NORMALIZATION**: without a canonical
   form, uniqueness can be bypassed by changing a capital letter (two accounts
   for one person) and login fails depending on how it is typed. It
   applies in THREE places — `/register`, `/login` and **`manage.py`**, the
   third is the one people forget; form checking itself is
   intentionally absent from `manage.py` (service roles without an address). The
   field remains named `username` ON THE WIRE (renaming it would break the form
   of every existing project): the CONTRACT says what it must contain.
   401 and never 422 at login — a malformed identifier does not exist, and
   saying so would teach the rule to an attacker. Converts NO existing
   accounts: they continue to work and are counted at startup
   (as at point 89). monl checks form, never whether an inbox receives mail —
   so no confirmation code or password reset by email; those are bricks that start
   with “monl knows how to send a message.”
   **The verifier must follow the rule it enforces**: the smoke
   test registered with hard-coded 'smoke' and got 422 on its OWN
   registration (`_identifiant_smoke`, smoke_test.py, derives the identifier from
   the contract). **`phone_prefix: "+33"`** makes “06…” and “+336…” canonical: without it
   the two notations are two accounts (limitation STATED, with its witness —
   monl makes you DECLARE what it cannot know, just as `min` arms stock at
   point 86). Tested by `tests/test_identifiant_de_compte.py` (47 tests).
   See point 95.
   **POINT 138, two corrections.** (a) The **guided dialogue never asked the
   question**: none of the ten templates declared an identifier, and every project
   created through the dialogue accepted `'!!!'` or two spaces as an account identifier
   (observed at `projets/AtelierNaya`, a workshop in Cotonou — reservations
   that cannot be honored because no one can be contacted, point 90 through
   another route). `_ask_account_identifier` asks it just after
   `_ask_self_register`, and ONLY if someone registers online. This is
   the counterpart of point 85: there a written rule produced nothing, here a
   brick that produces a lot was offered to nobody — **every brick that
   constrains an INPUT must be wired into the dialogue**, otherwise it protects
   only hand-written specs. (b) **`phone_prefix` canonicalized only a
   number beginning with `0`** — a European international prefix, inferred from the sole
   example `"+33"` used to write the rule. In Benin, numbers are written
   without a leading zero, so `"+229"` produced NOTHING: registered as
   `97123456`, login with `+22997123456` returned 401 (measured). The calling
   code now applies as soon as declared; a leading zero is removed if present,
   and an already-international number entered without `+` is never prefixed
   twice (otherwise the fix itself would create a third account). The TWO
   functions — `runtime.py` and `admin_cli.py` — must remain identical.
2. **`rule Entite.champ hidden`** — hides a field from all read responses
   (list + detail), for everyone. It remains in the database and remains
   writable. Implemented in `src/parser.py` (`masking_rule`)
   and `src/generator/routes.py`. Covered since point 64 by
   `tests/test_masquage_hidden.py`, against a real server: masked in
   list AND detail, logged in as anonymous, field still writable and
   still in the database (verified by direct SQLite read). It remains absent from
   all examples — coverage comes from the test, not a compilation.
3. **`rule Entite.Create decrements Entite.champ [by N]`** — decrements a
   numeric field on an entity linked to the creation of a record
   (typically a report). Compiled by `exemples/03_reseau_social.ml`
   (`Report.Create decrements Post.score`). **Refused on an entity named
   like an actor** (point 199, issue #89): its rows are linked to no account,
   while a client reads account ids under the same `<actor>_id` name, so the
   counter hit a random profile — the reporter's own, measured.
4. **`rule Entite.Create increments Entite.champ [by N]`** — symmetric to
   `decrements`, for likes/appreciations. Grammar: two distinct Lark productions
   (`decrement_rule`/`increment_rule`), not a single rule shared by keyword (avoids
   the Lark filtering trap that caused the first attempt to be cancelled).
   `ast_validator.py` validates both in the same loop, each rule carrying a
   `"direction"` field. `generator.py` chooses `+`/`-` based on that field.
   **Point 202 (issue #116): a field targeted ONLY by constant `increments … by N`
   is an EVENT counter held by the server** — absent from Create/Update bodies,
   starts at 0, `server_generated` in the contract, still fillable by `seed`.
   A field with any `decrements` or `increments … by champ` is a BUDGET (stock,
   score) and stays client-settable: making it server-held would stop a
   merchant from setting stock. Single source: `event_counter_fields`
   (`policies.py`).
   Compiled by `exemples/03_reseau_social.ml` and
   `exemples/05_classement.ml`.
5. **`rule Entite.champ categorized: "label" below N, ..., "label" otherwise`**
   — replaces an `Integer`/`Float` field with a category label in
   all read responses (list + detail), on the same principle as
   `hidden`, but substitutes instead of removing. General scope
   (any numeric field, not only those targeted by
   `increments`/`decrements`). Incompatible with `hidden` on the same field
   (explicit compilation error). The last tier must be
   `otherwise` (guarantees full coverage). Labels injected via `repr()`
   in generated code (never manually interpolated between quotation marks).
   Compiled by `exemples/03_reseau_social.ml` (`Post.likes` as few /
   popular / viral).
6. **Final assembly: anonymous social network** — all the bricks
   above combined in a single spec (today
   `exemples/03_reseau_social.ml`, successor to `17_anon_social_network.yaml`),
   each in its most natural role rather than stacked on the same
   entity (`Post` anonymous/public/categorized — author as pseudonym
   `generated`, brick 7 below — identified `Comment` with `ownedBy`).
   Two real bugs discovered while assembling it (not while
   rereading it), both resolved: a comment alone on its own line
   between two top-level blocks crashed compilation
   (`Tree` not transformed); a comment alone INSIDE an indented block
   (`entity`/`workflow`...) caused parsing to fail outright
   (`UnexpectedToken`). Fixed at the root in `src/parser.py`:
   `parse_monl_string()` removes every line that is ONLY a comment
   from the source text before Lark even sees it — one fix
   covering both cases, rather than 5 grammar rules to fix
   separately (entity/workflow/custom_block/ui_block/landing_block).
7. **`rule Entite.champ generated`** — removes a `String` field from the
   Pydantic schema of its entity's `Create` route; the server populates it
   itself with a stable anonymous pseudonym per account (`Anon#3821`, generated
   once at `/register`, carried by the JWT as `actor`/`user_id`).
   Closes the gap from point 29 (`Post.author` as free `String`, with no
   integrity guarantee). Incompatible with `hidden` on the same field, and
   with a `public` `Create` action on the same entity (no reliable identity
   from which to derive a pseudonym). Compiled by
   `exemples/03_reseau_social.ml` (`Post.author`).

8. **`rule Entite.Action accessibleBy col1, col2`** — two-part (or more)
   access control: the action is allowed only if the caller's JWT ID appears
   in one of the listed columns (sender through the auto-populated relation FK,
   recipient through a declared Integer field). List filtered by WHERE ... OR ...,
   detail/Update/Delete return 403 to third parties. At least two distinct
   columns (otherwise use `ownedBy`), blocking conflict with `ownedBy`, `public`
   takes precedence. Completes the “private messaging” brick mentioned as early
   as brick 1. Proven against a real temporary server by
   `tests/test_access_parties.py` (which includes its own spec), and compiled by
   `exemples/03_reseau_social.ml` (`PrivateMessage`).
   See point 31 of `docs/design_decisions.md`.

9. **`rule Entite.champ payable`** — the rule names the field that carries the
   AMOUNT, and therefore the entity being charged. Adds two tracking columns
   (`payment_status`, `payment_ref`, never supplied by the client) and two
   routes: `POST /entite/{id}/paiement` and `POST /paiement/webhook`.
   **The amount comes from the DATABASE, never the request body** — the payment
   route accepts no body, and rereads the field on every call. Seven compile-time
   refusals (entity or field missing, non-numeric field, combined with `hidden`,
   two `payable` fields on one entity, `public` creation, and since point 75 the
   absence of an incoming relation designating an owner — without it the payment
   route cannot return 403 to anyone). First OUTGOING call by a monl backend:
   secrets from the environment (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`),
   503 naming the missing variable, and the rest of the server intact —
   `monl run` and the smoke test remain green offline. The webhook verifies the
   provider's signature: this is the ONLY place in the generated backend where
   an unauthenticated third party writes to the database; never weaken it. The
   reference it reads is qualified by the entity name (`'Order:42'`, point 75)
   so an app with multiple `payable` entities never confuses IDs from two tables.
   Proven against a real server and an embedded fake Stripe by
   `tests/test_paiement.py`, and compiled by `exemples/02_boutique.ml`
   (`Order.totalAmount`). Available from the guided dialogue (`_ask_payable`,
   as soon as a `Money` field exists on an owned entity) since point 75,
   not only by writing the spec by hand. See points 74 and 75.

10. **`rule Entite.champ derivedFrom Entite.champ by champ`** — the named field
    on the left is CALCULATED BY THE SERVER from a linked row
    (`rule Order.total derivedFrom Product.price by quantity`), and disappears from
    request bodies — creation AND modification, since the Pydantic schema is unique
    per entity. Exists because `payable` reread from the database an amount the
    client had written there: **two proven exploits** (POST with `total: 0.01`,
    then PUT on an honest order), see point 77. Thirteen compile-time refusals;
    two are worth knowing: the multiplier must be `required` (otherwise calculation
    on nothing), and the source cannot be the owner (its FK comes from the token,
    so the client could not designate any row). The amount is **recalculated on
    PUT** — otherwise the flaw moves to the quantity — from the **stored** FK,
    never the request body's: monl's Update route does not write FKs, so calculating
    from `data.<fk>` allowed charging €89 for an item priced at €189 (verified,
    both directions tried). Proven against a real server by
    `tests/test_derivation.py`. See points 77 and 78.
    **`payable` now REQUIRES it** (point 79, the project's first breaking refusal):
    a client-writable amount makes compilation fail. The reasoning, not to reopen —
    the creator of a record is always its owner (`populate_owner` writes
    `current_user_id`), the owner is the only one who can pay (403 otherwise),
    so a writable amount is one the payer sets themselves. No legitimate case
    exists, not even an invoice issued by an admin: they would become its owner,
    and the client could not pay it.
    The refusal lives in a cross-check AFTER the two validation loops (it needs
    both lists); earlier `payable` refusals still trigger before it.

11. **`rule Entite.Action ownedBy Entite`** — **TRANSITIVE** ownership: “this
    row belongs to whoever owns its order.” No new syntax — this is the refusal
    from point 80 turned into a brick, provided the chain leads back to an actor.
    The reversal to understand: the ownership column is no longer derived from
    the token but **supplied by the client**, so it must be VERIFIED at creation
    (403, same response for “does not exist” and “not yours” — distinguishing them
    would allow enumeration of other people's orders). Access control becomes a
    join across the four paths: `IN` subquery for list, one-level traversal for
    detail (404), join returning the ACCOUNT ID for Update/Delete — leaving the
    comparison unchanged from the direct case. Four refusals: intermediate without
    an owner, two-level chain, ambiguous intermediate, direct+transitive mix. A
    fifth existed — `payable` on a transitive entity — **removed at point 87**:
    it protected against an incorrect comparison in the payment route, not an
    impossibility of the brick, and that route now uses the same join as Update
    and Delete. Proven against a real server by
    `tests/test_propriete_transitive.py`, with deliberately DIVERGENT IDs: the
    first attempt with the point 80 probe showed nothing because “user 1” and
    “order 1” coincided. See point 81.

12. **`rule Entite.champ sumOf Entite.champ`** — the named field is the SUM of a
    field from all CHILD rows, recalculated by the server on every row write. This
    is what `derivedFrom` could not do (it reads only ONE linked row), and thus
    what makes an order with multiple items priceable — and chargeable:
    `payable` now accepts a `sumOf` field.
    **Recalculate, never adjust**: `total = total + x` desynchronizes as soon as
    a write fails, and nothing fixes it; the sum is reread from the table, with
    `COALESCE` (emptied cart → 0, never NULL) and `ROUND` (a floating-point sum
    drifts, and this is an amount). Three branches, and the third is the one
    people forget: creation (in THE SAME transaction as insertion), modification
    (parent reread FROM THE DATABASE, never `data.<fk>` — lesson from point 78),
    deletion (parent read BEFORE DELETE, after which the foreign key has vanished).
    **The refusal that defines the brick**: summing an amount the client writes
    still gives them control of the total, with just one more addition — the point
    77 flaw through the cart door. This refusal lives in the cross-check with
    `payable`, NOT in the `sumOf` loop, because summing a client field remains
    legitimate outside payment (`Commande.nbArticles sumOf Ligne.quantite`
    counts items, it charges nothing): the combination is the problem.
    Proven against a real server AND a fake Stripe by `tests/test_agregation.py` —
    the amount is checked against what the PROVIDER receives. Compiled by
    `exemples/02_boutique.ml`, now a real cart. See point 82.

13. **`assets` + `Image` type** — files supplied by the HUMAN (photos,
    logo, favicon) declared in the spec, and **checked for presence at
    compilation**. Born from a usability question, led somewhere else: three
    faulty paths (missing file, mistyped folder/extension, `/etc/passwd`)
    all compiled silently, and a broken image is only noticed by eye, in
    deployment. Two groups of checks, deliberately separate — **form** (absolute
    path, `..` traversal, remote URL under `Image`) always active because they
    are pure; **existence** only when `base_dir` is known, otherwise the validator
    keeps QUIET rather than guessing. `Image` means a LOCAL file: a URL is refused
    because monl makes no network calls and could not assert anything about it —
    `String` remains available for an unverified remote address.
    **The folder lives OUTSIDE `frontend/`**: that folder is renamed by
    `monl frontend` and its allowlist excludes `.jpg`, so photos deposited there
    ended up in `frontend.precedent/` without a word — this was the most serious
    failure in the series. The contract's `media` role now comes from the TYPE
    rather than the name (`MEDIA_HINTS` is only a fallback).
    “Exists” does not mean “served”: the smoke test mounts the project with the
    SAME wrapper as `monl run` (via `serving.py`, a deliberate leaf to avoid the
    cli↔smoke_test cycle) and makes a real GET for every asset. **Asset mounting
    must precede `/site` mounting** — reversed, three 404s. Proven by
    `tests/test_assets.py`, adopted by `projets/SneakerLab`. See point 83.
    **Layer 2 (point 84): `monl assets add <fichier> --for "Halo RS"`**, plus
    `--logo` / `--favicon` and `monl assets list`. It copies, renames to a slug,
    writes the declaration to the spec — and REVALIDATES the result with the real
    parser and real validator before saving it: *the tool writes, the compiler
    proves*. Three things not to undo. **Editing is TEXTUAL**
    (`src/monl/assets_tool.py`), never a parse → regenerate round trip: a real
    project's spec is more than half comments, and those explain the bricks in use.
    **Revalidation runs WITHOUT `base_dir`**, while the existence of what the tool
    writes is checked separately through `resoudre_asset` — the first version
    validated everything with `base_dir`, which had two downsides: `list` could
    not report a missing asset, and `add` was unusable on a spec declaring two
    missing photos. Lesson to remember: **a guarantee that's too broad isn't safer;
    it's wrong somewhere else.** And **the tool deletes nothing, writes no credit,
    and does not recompile** — an orphan is reported, `monl update` remains the
    explicit action. `resoudre_asset` / `candidats_asset` (`ast_validator.py`) are
    the SINGLE source of resolution, shared by the compiler's refusal and the
    tool's report. Proven by `tests/test_assets_tool.py` (33 tests); it is what
    placed the logo and favicon in `projets/SneakerLab`.
    13bis. **Brick 26 (point 115): `monl content export`/`import`** — replace the guided
    dialogue's placeholder content in bulk with real text and real photos, without
    editing the DSL by hand. `export` writes `content/<Entite>.csv` (one column per
    field, except those the client can never provide — same exclusion as the
    Create/Update schema) and `content/LISEZMOI.txt`; `import` REPLACES each
    entity's entire `seed` block from the CSV (no row-by-row merge). Reuses WITHOUT
    REWRITING the point 84 discipline (`_valider`/`_revalider`, `_blocs_seed`,
    `_litteral`, `resoudre_asset`, imported from `assets_tool.py`). A catalog child
    entity (brick 21) gets a `_parent` column; non-contiguous `seed` blocks for
    the same entity cause import to refuse rather than guess where to write.
    `src/monl/content_tool.py`, `tests/test_content_tool.py` (8 tests) — also
    proven on a real compiled project (export → real CSV and photo edit → import →
    `monl update` → real server).

14. **`required` / `unique` / `min` / `max` finally enforced** (point 85) — the
    compiler's four OLDEST rules did **nothing**: byte-identical output with or
    without them, and a phantom reference silently accepted (`rule
    Colis.champFantome required` compiled). `exemples/02_boutique.ml` declared
    `rule Product.price min 0` and the server wrote `price: -99` to the database —
    in a shop where the price is multiplied, summed, and sent to Stripe. Now:
    references validated, `min`/`max` as Pydantic constraints (422 before any

15. **`rule Entite.Create decrements Entite.champ by champ`** — decrement WHAT

    the targeted column is the one that points to the DECREMENTED entity, not the

16. **`rule Entite.champ timestamp`** — the moment of CREATION, written by the
    server in ISO 8601 UTC and never afterward. The field must be `DateTime` and
    disappears from request bodies, for both creation AND modification: a date
    you give yourself proves nothing. Born from the back office in point 88 — an
    order book without dates says neither what is recent nor in what order to
    fulfill orders. **Three decisions not to reopen.** `Date` is REFUSED, with an
    explanation: truncating to the day would lose information the server has and
    make two records from the same day impossible to order. The **millisecond**
    is not overkill: at second-level precision, two orders placed one after the
    other had the same date, and the sort promised by the contract became wrong
    exactly when an order book needs it. And **older records remain `NULL`**:
    the additive migration (point 32) catches up a column, never its contents; a
    `DEFAULT CURRENT_TIMESTAMP` would date the day-before-yesterday's orders as
    today — a database that LIES, worse than an empty cell. The server COUNTS
    them and names them at startup, and the contract tells the AI to display a
    dash. No refusal of combinations was written: `generated` requires
    `String`, `derivedFrom`/`sumOf`/`payable` require numeric types — the type
    refusal happens first, and an unreachable refusal would suggest protection.
    `required`/`min`/`max` are inherited from the cross-check in point 85 without
    adding a line. Proven by `tests/test_horodatage.py` (20 tests), compiled by
    `exemples/02_boutique.ml`, adopted by `projets/SneakerLab`, and **emitted by
    the guided dialogue without asking a single question** (the only useful
    answer would be “yes”). See point 89.

17. **`rule Entite.Create requiresOwn Entite`** — the caller must ALREADY own a

18. **The lock on a paid record** — no new syntax: it is `payable` (brick 9)

20. **`rule Entite.champ "valeur" releases Entite`** — reaching a VALUE undoes

## Four actions on a running site, and which one to choose

- **`monl diff`** (point 103) — the question posed by `monl update`, asked WITHOUT writing
  anything. Compiles into a temporary directory, prints the SAME report
  (`_rapporter_delta` is shared — two delta calculations would diverge, and
  six points have struggled to keep this calculation right), and exits.
  No project file is touched, including the reference contract.
- **`monl update`** — the SPEC has changed. Recompiles and reports the contract
  delta (routes, fields, access, read-only, prerequisites, locks, content,
  relationships).
- **`monl retouche "<ce qui cloche>"`** (point 93) — the spec has NOT changed, the
  site is simply correct with respect to the contract, but something looks wrong.
  Fixes it without rebuilding, backs up to `frontend.precedent/`, and **fails
  if the AI changes nothing** (for a touch-up, doing nothing means the request
  was not handled — not a neutral state as at point 73).
- **`monl frontend`** — rebuild from the contract. The heaviest action:
  a non-deterministic draw that can lose what you liked.

The trap to know: **a display defect is not always a frontend defect.** The
SneakerLab FAQ came out jammed together because the SPEC held four
questions in one string (point 94) — a touch-up would have made the AI guess,
and the structure would have been lost again on the next rebuild. The touch-up
instruction now says to FLAG this case rather than work around it. Before
making a touch-up: does the content really say what we want to see?

- POINT 96: `requiresOwn` has a counterpart on deletion (`_profile_dependents`,

- **THE VERIFIER IS A CLIENT LIKE ANY OTHER** (points 95, 96, then 100):
  any brick that constrains INPUT also constrains the smoke test, which hardcodes

  refused by `oneOf`; at point 101 the question was asked BEFORE writing the

  the parent designation made it fail silently, even though the AST contained
  the block. This question joins the one about `_contract_signature` in the
  list to ask BEFORE writing a brick.
- POINT 105: **does the directory exist, THEN does it contain a project.**
  `_load_state` returns `None` in both cases, and the four entry points
  concluded the latter — `monl frontend` even advised “run 'monl compile'” for
  a directory never found. `_erreur_de_chemin` (cli.py) asks the first

  **`retouche` is the ONLY command whose first argument is not the directory**
  (`run`, `update`, `diff`, `compile`, `frontend` all take it first): the
  inversion is therefore the expected error, it is DETECTED and NAMED — never
  corrected automatically, since that would be guessing. The witness to
  preserve: a false positive would refuse a well-written retouche.
- POINT 97: the agent's output is PRESERVED and displayed when nothing changed.
  `run_cli_agent` already returned it; no one read it — monl displayed

  as a diagnosis is worse than a vague message**: it sends people to fix
  something that is not broken. The rephrasing advice now appears only if the
  agent said nothing.
- The paragraph separator **`¶`** (point 64) structures the body of a

  STRING_LITERAL, and `paragraphes()` (`frontend_contract.py`) translates it
  back. Keep this in mind BEFORE considering a brick: “I don't want a
  paragraph” was solved this way (point 97).
- POINT 93: there is only ONE path to AI — `_lancer_ia` (`cli.py`) and

  The dispatch called the online model; copying those lines for retouching

  malicious agent THROUGH the retouch path to verify this.
- POINT 94: `landing` accepts `question "…": "…"`, repeatable like `section`.
  Intentionally FLAT form — an indented sub-block would have added a level to

  can recover it afterward. The brief must say that this is a LIST — simply
  providing the pairs without saying so led to recreating the prose block we

- POINT 92: the warning “paths absent from the contract” (`cli.py`) excludes
  NAVIGATION routes, recognized by the `#/x` present in the same file. It
  flagged four correct routes on SneakerLab. A warning that is wrong about a
  correct site teaches people to stop reading warnings — the same decision as
  point 57, about the same warning. Keep its witness: a genuinely faulty path
  must still be reported.
- `min` on a decremented field ARMS the availability check
  (`routes.py`, point 86). This is not a coincidence to preserve through
  discipline: it is the only declarative way to distinguish stock (which must
  not go below zero) from reputation (which can). Wiring in a “stock” exception
  instead would reopen the question with every new case.
- `src/monl/assets_tool.py` is the repository's ONLY location, outside the
  guided dialogue, that writes to the human's spec (point 84). Three rules
  cover everything there: TEXTUAL editing (comments are project
  documentation, and a parse → regenerate round trip would erase them),
  revalidation by the real parser + validator BEFORE writing, and full rollback
  on failure (remove the copied file, restore an overwritten file under
  `--force`). Do not reintroduce `base_dir` into `_valider`: the existence
  check is limited to what the tool WRITES; otherwise `list` becomes unable to
  report a missing item again, and `add` becomes unusable with an incomplete
  spec.
- **POINT 154: `generator/core.py` is reduced to `__init__` + seven mixins, and
  `parser` is a PACKAGE.** The mixins in `generator/`:
  `pipeline` (including `_compute_route_map`), `modele`, `proprietaire` (including
  `_transitive_chain`, `_owner_lookup_sql`, `_identity_fk_columns`), `calculs`,
  `paiement` (including `_payment_locked_parents`),
  `sql_colonnes`, `prealables`. The UNIQUE sources cited below in this file
  have therefore changed modules, not roles.
  **THE PITFALL TO KNOW FOR ANY LARK TRANSFORMER SPLIT**:
  `@v_args(inline=True)` on a CLASS skips every inherited method
  (`name in libmembers and name not in cls.__dict__` → `continue`). Moving
  productions into bare mixins would have left them unwrapped: they would have
  received a LIST of children instead of inlined arguments, without raising an
  error on any line. Each mixin therefore inherits from `Transformer` and has
  its OWN `@v_args` — verified by execution (73 productions, 73 wrapped).
  **A class decorator does not follow code that is moved.**
  `parser/grammaire.py` exceeds 400 lines ON PURPOSE: the grammar is ONE
  declarative artifact, Lark ignores rule order, so any split would be
  arbitrary. The exception is documented in the file's docstring.
  **And the third form of the same defect** (after 152 and 153): two
  `per-file-ignores` in `pyproject.toml` targeted files that had become
  packages — they no longer excused anything, and `ruff` does not complain
  about an orphaned path. A witness in `tests/test_architecture.py` now rejects
  this. **A guarantee that no longer applies to anything makes no noise: the
  suite stays green all three times.**
- **POINT 153: `frontend_ai` is a PACKAGE, and an attribute replacement targets
  the module where the name is LOOKED UP.** Eleven modules (`fondations`,
  `fournisseurs`, `reponse`, `squelette`, `controles_design`,
  `controles_fichiers`, `redaction`, `etages`, `images`, `agents`,
  `orchestration`). **Internal rule: a call between package modules goes
  through the MODULE object** (`reponse._write_files(…)`), never a bound name —
  this gives one replacement point per function instead of one per caller. So
  a test writes `monkeypatch.setattr(frontend_ai.agents, "_fingerprint_protected", …)`
  and not `setattr(frontend_ai, …)`; the latter no longer takes effect,
  SILENTLY.
  **What this revealed**: the agent path test passed without exercising the
  fingerprint safeguard from point 73 — the real function ran and returned an
  empty dictionary. Counter-proof with a raising stub: reached when it targets
  `.agents`, never reached when it targets the package. The imports from
  `cli.py` to `frontend_ai` are INSIDE functions, so they resolve after the
  replacement: those still take effect.
  Two corollaries for the next split: **a module name must not resemble any
  local variable in the code it receives** (`brief` and `socle` targeted the
  variable, not the module — `ruff` F823), and **a public surface is measured
  with an AST**, never `grep` (multiline imports and attribute access evade
  text search).
- **POINT 152: the validator is a PACKAGE (`src/monl/ast_validator/`).**
  Same shape as `generator/`: one module per concern, the class recomposed from
  mixins in `core.py`. Add a new rule in the module for its layer — `acces.py`,
  `champs.py`, `commerce.py`… — never in `core.py`. Execution order comes from
  the pipeline (`validation_pipeline.py`), NOT base-class order. `socle.py` is
  the LEAF (constants + `ASTValidationError`) and reads nothing from its
  package: that is what makes a cycle impossible, and a test verifies it
  instead of leaving it to discipline. The public surface has not changed —
  `from monl.ast_validator import MonlAST, ASTValidationError,
  DEFAULT_ASSETS_DIR, resoudre_asset`.
  **What the split uncovered**: `tests/test_architecture.py` named `generator`
  HARDCODED in `MODULES`, so `ast_validator` fell out when it became a package
  — its contract remained written in `INTERDITS` while checking nothing, and
  no test turned red. The list is read from disk, and a witness requires every
  contract to apply to a known module. **An architecture test stops watching
  in two ways: it no longer sees imports, or it no longer sees modules — the
  latter leaves no trace.** Any structural-only change is proven by
  `tests/test_golden_artifacts.py`: all eleven fingerprints must remain
  UNCHANGED. And **never run a counter-proof while a suite is running**: a
  subprocess rereads the disk, while the main pytest process already has its
  import in memory.
- **POINT 151: a MODEL's demonstration dataset is adapted by AI, in
  `src/monl_platform/seed_ai.py` and nowhere else.** Every shop sold “Kyoto
  Teapot”: the description reached only the `brief`, meaning TEXT, never the
  data. The guided dialogue remains deterministic — the platform customizes,
  since it already calls AI. **AI writes CSV ROWS, never the structure**: the
  header comes from `monl content export`; a different header makes the
  response be rejected. Writing goes through `importer_contenu` (point 115),
  and therefore through the real parser — no new machinery. A failure restores
  the original CSV: a generic catalog is a defect, a lost build is a bill. A
  spec PROVIDED by the user is never touched. The call carries the product's
  quota safeguard.
- **POINT 150: an UNDETERMINED measurement is not a NULL measurement.**
  `_frontend_fetch_calls` (`cli.py`) counted an access function only when
  written as `fetch(endpoint, …)`; the model wrote `const url =
  \`${API_BASE}${endpoint}\`; fetch(url, config)`. Result: “0 routes out of
  15” on a frontend that called five, and whose smoke test passed — properly
  refused. And the stage instruction says “factor the code”: monl asked for
  factoring and then refused the factored site. The check now follows the
  parameter FLOW (direct, template, local variable) while remaining
  conservative — it requires a demonstrable flow; otherwise any function
  containing a `fetch` would have its arguments counted as routes. **The
  meaning of the error matters**: for a phantom route, not counting the
  irreducible case is right; for coverage, that accuses a correct site.
- **POINT 149: the budget requested of a stage comes from the CONTRACT, never
  a constant.** monl demanded “about 1,500 tokens” for `app.js` whatever the
  contract, with a hard limit of 12,000 characters — for a file whose complete
  examples in the repository weigh 26 to 43 KB. The model obeyed to the token
  (1,698 measured, ZERO retry: nothing was truncated), then monl refused it
  for incompleteness. **Changing models cannot help**: the stronger model
  obeys better, and therefore produces less. Ceiling-without-a-floor for the
  third time — and this is the NUMBERED instruction, the last one read, that
  the model listens to. The floor is now stated at the stage, and the hard
  limit follows the budget instead of contradicting it.
- **POINT 148: where a build's money goes, measured.** `styles.css` consumes
  50% of OUTPUT tokens (the part with no function), `app.js` 34% even though
  it carries all the completeness. The “retries” of a stage come from an
  UNREADABLE response: wrapping a JS file in a JSON string breaks with cheaper
  models, and the retry pushes them toward what PARSES, hence toward the
  minimal file. Hence the fenced block fallback (`_fichier_depuis_un_bloc`) —
  fallback only, going through `_validate_files` like everything else. **The
  real cost lever is `--model-for`:** strong model for `app.js`, cheaper model
  for `styles.css`.
- **POINT 147: automatic correction keeps the BEST attempt, not the last.**
  Measured with real spend: when asked to fix two lines, the model rewrote the
  site and lost 14 of 15 routes — and monl kept that version, because the loop
  returned the final state. Ranking is `(errors, warnings)` without weighting
  (inventing severity would be an opinion disguised as measurement); reported
  errors are those of the RETAINED files; restoration touches only the
  allowlist, never generated images, and removes files from the discarded
  attempt — mixing the two would be worse than either. Counter-proof required:
  a second, BETTER attempt must remain in place, or the safeguard cancels the
  automatic correction and is deemed to have passed.
- **POINT 146: a brick without a PRODUCER does not exist.** Brick 30
  (footer links) had been declarable since point 144 and nothing wrote it —
  neither the guided dialogue, nor the ten templates, nor the web console:
  every site came out with a footer without a destination. This is point 85
  in a different light, and the compilation test cannot see it.
  **Question to ask for every new brick, alongside the one about
  `_contract_signature`: who will write it?** Address completion has ONE source
  (`adresse_de_lien`, dialogue_engine.py); the console necessarily has a
  JavaScript copy, and `tests/test_liens_pied_de_page.py` runs BOTH on the
  same inputs — two implementations of the same rule always diverge.
  Express mode asks no questions: its links arrive through
  `express_links`.
- **Never slice a test scenario using a negative range.**
  `SCENARIO_PORTFOLIO[:-4]` broke eight tests at once when the first question
  was added, without ever saying what it removed; scenarios are now
  composed of named pieces, and the number of proposed entries is READ from
  `GuidedDialogue.LIENS_PROPOSES`.
- **POINT 145: Google/GitHub sign-in lives in
  `src/monl_platform/oauth.py`, and nowhere else.** Four decisions are written
  there and are not reopened: the provider's identity has its OWN namespace
  (`github:<id>`) — no automatic linking to a password account with the same
  address, or one would take control of the other; only an address VERIFIED
  by the provider is accepted (otherwise the brick moves the arbitrary string
  instead of closing it); `state` is signed AND dated (replay, like webhook
  signing in point 91); and the return address comes from
  `MONL_PLATFORM_PUBLIC_URL`, **never** from the `Host` header — its absence
  prevents STARTUP as soon as a provider is configured, rather than letting a
  button return 503 when clicked. The token travels in the FRAGMENT (never
  sent to the server, never logged), and the console clears the address bar
  after retrieving it. Proven with an EMBEDDED FAKE provider
  (`MONL_OAUTH_*_BASE_URL`, precedent of the fake Stripe provider in point 74)
  and with a jsdom driver against the real server. **The test harness trap**:
  jsdom has no `matchMedia`, so the console script dies on its first line and
  we measure the harness instead of the product.
- **A passing test does not prove it bites** (point 145). The refusal of a null
  `password_hash` in `authenticate_account` could be removed while leaving the
  entire suite green: `_password_matches` already ruled it out one layer
  lower. Removing a safeguard to see a test fail is the only way to know where
  the guarantee really lives.
- The smoke test (src/smoke_test.py) starts a TEMPORARY server in a temporary
  directory: it never touches the project's app.db. The jsdom fetch MUST be
  injected via beforeParse (real bug: assigned after construction, it is never
  seen by the page scripts).
- The contract declares `api.base_url = ""` — SAME ORIGIN, never an absolute
  URL or hard-coded port: `monl run` mounts frontend/ at /site on the server
  that already hosts the API. Putting an absolute base URL back would break
  `monl run --port` and cause the smoke test (temporary port) to reject any
  compliant frontend. The jsdom shim explicitly refuses absolute URLs instead
  of rewriting them: rewriting them would be a false positive. Point 51.
