ACT 01

The dialogue — no AI, no network

./monl

The script monl at the root calls src/cli.py → main(). Without arguments, cmd_init() (ligne 91) takes over.

  1. 1

    The engine asks the questions, the presentation dresses them up

    dialogue_engine.py never receives stdin: it consumes a function ask(prompt). In real use, it is input ; in tests, an iterator of scripted responses. That is why the tests run the real dialogue instead of simulating it.

    tui.py only handles formatting. The engine knows it only through the interface PlainDialogueUI — bare rendering by default, so it is unaffected by presentation.

    Boundary

    No dialogue logic in tui.py, no formatting in dialogue_engine.py. Mixing them breaks scripted tests.

  2. 2

    The catalog pre-fills everything

    app_templates.py contains 10 application templates — entities, actors, rules, demo data, editorial sections. These are data, not code: the dialogue assembles them with the same emitter as free mode.

  3. 3

    The spec is revalidated before it is written

    At the end of the journey, the generated text goes through the real parser and audit again. A catalog template therefore cannot produce a broken spec without immediately breaking compilation.

    written MonProjet/spec.ml

ACT 02

Compilation — the core, unchanged since the pivot

monl compile spec.ml

cli.py:68 compile_project() delegates to the historical compiler, main.py compile_monl(), then adds the contract layer. Three steps, always the same.

  1. 1

    Parsing

    parser.py — Lark grammar with indentation. Before Lark sees anything, _strip_standalone_comment_lines() removes lines that contain only a comment: two real parsing bugs were fixed there, at the root, rather than in five grammar rules.

  2. 2

    Static audit

    ast_validator.py — MonlAST.validate_and_audit() normalizes the AST and refuses dangerous specs: privilege collisions, ownership without structure, and rules that conflict with one another. An error should appear here, not on screen.

  3. 3

    Generation

    generator/ is a mixin package recomposed in core.py:18. Each layer has its module: sql_schema, runtime (JWT secret, connection, migrations, register/login), routes (one route per action/entity pair + access control), schemas, theme, sandbox, admin_cli.

    written app.py schema.sql sandbox_ai.py manage.py .jwt_secret
    Where to make changes

    A new generation brick belongs in the module for its layer, never in core.py. The JWT secret belongs to the project and is never regenerated by recompilation.

ACTE 03

The contract — what monl tells the AI that will design the interface

Since the pivot, monl no longer generates any frontend. frontend_contract.py build_contract() (line 182) translates the AST into a document for a UI AI: exact routes, roles, fields and their display role, screen archetype, design direction, and the editorial text entered during the dialogue.

written frontend_contract.json FRONTEND_PROMPT.md CLAUDE.md monl.json

The two clauses not to touch

Single source

_compute_route_map() (generator/core.py:376) is shared by FastAPI generation and the contract. Duplicating this logic elsewhere would make the advertised API diverge from the actual API — a test compares the contract with the decorators actually written in app.py.

Same origin

api.base_url is the empty string. Never use an absolute URL or a hard-coded port: monl run mounts the frontend at /site on the server that already hosts the API. Putting an absolute base URL back here would break --port and cause any compliant frontend to fail.

monl.json stores the spec path and two SHA-256 fingerprints (compiled spec, contract). This file will later make it possible to detect a spec that was changed but not recompiled.

ACTE 04

The frontend AI — three paths, the same safeguards

frontend_ai.py. Whichever path is used, the permitted scope is the frontend/ directory alone, and the result goes through the same checks as everything else.

Through the API

monl frontend

Key in ANTHROPIC_API_KEY. The brief is sent, the result comes back, and it is checked.

Through a subscription

monl frontend --provider claude-code

The agent works directly in the directory. The turn budget can be set with --max-turns.

Without a key

monl import <source>

Paste the brief into claude.ai, then download, install, and check the result.

Sealed

Before and after the agent runs, _fingerprint_protected() compares the fingerprints of app.py, schema.sql, the contract, and the spec. If even one byte has changed, the command refuses the result and sends you back to your version control.

ACTE 05

Verification — static, then behavioral

monl run
  1. 1

    Consistency

    cli.py:114 check_coherence(): does the spec match its fingerprint? Are the artifacts present? Was the contract edited by hand? Does the frontend call paths missing from the contract?

    The last check warns without blocking — a path may be built dynamically, and before it was narrowed, the warning raised a false alarm for every single-page application.

  2. 2

    Smoke test

    smoke_test.py run_smoke_test() starts an ephemeral server in a temporary directory, with a fresh database: it never touches the project's app.db. The contract routes are exercised over real HTTP; if Node is available, the frontend is run in jsdom.

    Why this is here

    Static consistency does not guarantee that things work. Several real bugs — the order of FOREIGN KEY constraints, a collision with a reserved SQL keyword, over-escaping between templating layers — would never have been uncovered by review.

  3. 3

    Launch

    If a frontend/ directory exists, cmd_run() writes a wrapper serve.py that mounts the directory at /site — without ever modifying app.py — then runs uvicorn serve:app. Otherwise, it runs app:app directly.

ACTE 06

Evolution — the delta, not a rebuild

monl update

cmd_update() (cli.py:299) rereads the old contract's signature, recompiles, then compares: routes added or removed, fields added or removed. If there are changes, it writes an instruction ready to give to the frontend AI.

written FRONTEND_UPDATE_PROMPT.md
Data preserved

The existing database is not rebuilt: new columns are added through an additive migration when the server starts.

The working rule that explains everything else

Every change is proven through actual execution: compile for real, restart a real server, make real requests, run the suite. Never rely on code review alone. That is why the tests start servers and run the real dialogue instead of simulating it — and why they are slow.

python3 -m pytest tests/ -q
