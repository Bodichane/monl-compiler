ACTE 01

Le dialogue — aucune IA, aucun réseau

./monl

Le script monl à la racine appelle src/cli.py → main(). Sans argument, c'est cmd_init() (ligne 91) qui prend la main.

  1. 1

    Le moteur pose les questions, la présentation les habille

    dialogue_engine.py ne reçoit jamais stdin : il consomme une fonction ask(prompt). En usage réel c'est input ; en test, un itérateur de réponses scriptées. C'est pour ça que les tests exécutent le vrai dialogue au lieu de le simuler.

    tui.py ne fait que la mise en forme. Le moteur ne le connaît que par l'interface PlainDialogueUI — rendu nu par défaut, donc insensible à l'habillage.

    Frontière

    Aucune logique de dialogue dans tui.py, aucune mise en forme dans dialogue_engine.py. Les mélanger casse les tests scriptés.

  2. 2

    Le catalogue pré-remplit tout

    app_templates.py tient 10 modèles d'applications — entités, acteurs, règles, données de démo, rubriques éditoriales. Ce sont des données, pas du code : le dialogue les assemble avec le même émetteur que le mode libre.

  3. 3

    La spec est revalidée avant d'être écrite

    En fin de parcours, le texte produit repasse par le vrai parseur et le vrai audit. Un modèle du catalogue ne peut donc pas produire une spec cassée sans casser la compilation immédiatement.

    écrit MonProjet/spec.ml

ACTE 02

La compilation — le cœur, inchangé depuis le pivot

monl compile spec.ml

cli.py:68 compile_project() délègue au compilateur historique, main.py compile_monl(), puis ajoute la couche contrat. Trois étapes, toujours les mêmes.

  1. 1

    Analyse syntaxique

    parser.py — grammaire Lark avec indentation. Avant que Lark ne voie quoi que ce soit, _strip_standalone_comment_lines() retire les lignes qui ne sont qu'un commentaire : deux bugs de parsing réels ont été fermés là, à la racine, plutôt que dans cinq règles de grammaire.

  2. 2

    Audit statique

    ast_validator.py — MonlAST.validate_and_audit() normalise l'AST et refuse les specs dangereuses : collision de privilèges, propriété sans structure, règles incompatibles entre elles. C'est ici qu'une erreur doit apparaître, pas à l'écran.

  3. 3

    Génération

    generator/ est un package de mixins recomposés dans core.py:18. Chaque couche a son module : sql_schema, runtime (secret JWT, connexion, migrations, register/login), routes (une route par couple action/entité + contrôle d'accès), schemas, theme, sandbox, admin_cli.

    écrit app.py schema.sql sandbox_ai.py manage.py .jwt_secret
    Où intervenir

    Une nouvelle brique de génération va dans le module de sa couche, jamais dans core.py. Le secret JWT est propre au projet et n'est jamais régénéré par une recompilation.

ACTE 03

Le contrat — ce que monl dit à l'IA qui dessinera l'interface

Depuis le pivot, monl ne génère plus aucun frontend. frontend_contract.py build_contract() (ligne 182) traduit l'AST en un document destiné à une IA UI : routes exactes, rôles, champs et leur rôle d'affichage, archétype d'écran, direction de design, et le texte éditorial saisi au dialogue.

écrit frontend_contract.json FRONTEND_PROMPT.md CLAUDE.md monl.json

Les deux clauses à ne pas toucher

Source unique

_compute_route_map() (generator/core.py:376) est partagé entre la génération FastAPI et le contrat. Dupliquer cette logique ailleurs ferait diverger l'API annoncée de l'API réelle — un test confronte le contrat aux décorateurs réellement écrits dans app.py.

Même origine

api.base_url vaut la chaîne vide. Jamais d'URL absolue ni de port en dur : monl run monte le frontend sur /site du serveur qui porte déjà l'API. Y remettre une base absolue casserait --port et ferait recaler tout frontend obéissant.

monl.json retient le chemin de la spec et deux empreintes SHA-256 (spec compilée, contrat). C'est ce fichier qui permettra de détecter, plus tard, une spec modifiée mais non recompilée.

ACTE 04

L'IA frontend — trois voies, mêmes garde-fous

frontend_ai.py. Quelle que soit la voie, le périmètre autorisé est le seul dossier frontend/, et le résultat repasse par la même vérification que le reste.

Par API

monl frontend

Clé dans ANTHROPIC_API_KEY. Le brief part, le résultat revient, il est vérifié.

Par abonnement

monl frontend --provider claude-code

L'agent travaille directement dans le dossier. Budget de tours réglable par --max-turns.

Sans clé

monl import <source>

Brief collé dans claude.ai, résultat téléchargé puis installé et vérifié.

Scellé

Avant et après le passage de l'agent, _fingerprint_protected() compare les empreintes de app.py, schema.sql, du contrat et de la spec. Un seul octet modifié : la commande refuse le résultat et vous renvoie à votre gestion de versions.

ACTE 05

La vérification — statique, puis comportementale

monl run
  1. 1

    Cohérence

    cli.py:114 check_coherence() : la spec correspond-elle à son empreinte ? Les artefacts sont-ils là ? Le contrat a-t-il été édité à la main ? Le frontend appelle-t-il des chemins absents du contrat ?

    Le dernier point avertit sans bloquer — un chemin peut être construit dynamiquement, et l'avertissement criait au loup sur toute application monopage avant d'être resserré.

  2. 2

    Smoke test

    smoke_test.py run_smoke_test() démarre un serveur éphémère dans un dossier temporaire, sur une base neuve : il ne touche jamais l'app.db du projet. Les routes du contrat sont éprouvées en HTTP réel ; si Node est disponible, le frontend est exécuté dans jsdom.

    Pourquoi c'est là

    La cohérence statique ne garantit pas que ça fonctionne. Plusieurs bugs réels — ordre des contraintes FOREIGN KEY, collision avec un mot-clé SQL réservé, sur-échappement entre couches de templating — ne se seraient jamais révélés par relecture.

  3. 3

    Lancement

    Si un frontend/ existe, cmd_run() écrit un wrapper serve.py qui monte le dossier sur /site — sans jamais modifier app.py — puis lance uvicorn serve:app. Sinon, app:app directement.

ACTE 06

L'évolution — le delta, pas la reconstruction

monl update

cmd_update() (cli.py:299) relit la signature de l'ancien contrat, recompile, puis compare : routes ajoutées ou retirées, champs ajoutés ou retirés. S'il y a du changement, il écrit une consigne prête à donner à l'IA frontend.

écrit FRONTEND_UPDATE_PROMPT.md
Données préservées

La base existante n'est pas reconstruite : les nouvelles colonnes sont ajoutées par migration additive au démarrage du serveur.

La règle de travail qui explique tout le reste

Chaque changement est prouvé par exécution réelle : compiler pour de vrai, relancer un vrai serveur, faire de vrais appels, lancer la suite. Jamais par relecture de code seule. C'est pourquoi les tests démarrent des serveurs et exécutent le vrai dialogue plutôt que de le simuler — et pourquoi ils sont lents.

python3 -m pytest tests/ -q

Carte du dépôt monl au 27 juillet 2026 — 137 tests, 6 765 lignes sous src/. Le quoi et le comment sont ici ; le pourquoi de chaque règle est dans docs/design_decisions.md.
